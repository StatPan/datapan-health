# Bounded Registry operation read model

The v2 read model is a Health-owned projection over the exact Registry operation-observation-plan release and the separately pinned Korean metadata artifact. It does not replace the fixed ten-canary `/datapan/v1/status`, `/datapan/v1/dependencies`, or `/datapan/v1/services` contracts.

`schemas/datapan.health-registry-operations-page.v2.schema.json` defines a page of at most 50 operations. The page binds the Registry source revision, release-manifest digest, plan-index digest and plan-schema digest, and independently binds the API metadata revision, source snapshot digest, catalog digest, generated metadata-artifact digest, and expected entity/operation counts. Those Registry revisions are independent pins and are not required to be equal. The page carries the exact v2 schema digest separately.

Operation identity is `(source_id, registry_operation_id)`. A data.go.kr API join is accepted only when `source_id` is exactly `data_go_kr`, the operation ID matches the 64-hex `registry_operation_id` in the metadata artifact, and the plan's `dataset_id` exactly equals that metadata operation's `dataset_id` and parent `registry_api_id`. The complete operation identity sets must agree before the reader is published. ECOS, KOSIS, Open Assembly, and Seoul rows stay operation-only with `api_id: null` until their own API metadata inventories are pinned.

`NewOperationReadModel` verifies and reads each pinned plan shard once, builds sorted in-memory indexes by operation identity and API ID, and accepts a bounded list of safe metadata projections and latest durable-attempt projections. `LookupAPIProgress` accepts no more than 50 unique exact API IDs and returns per-API total functions, configured/admitted functions, current pass/fail, claimed, attempted, stale, unobserved, delivery-pending, readback-verified, and enum-keyed missing reasons. A zero-operation API is reported as `no_registered_operations`, not as a healthy API. A read-model source failure is returned as an error so the caller can mark the requested APIs unknown and show a separate source warning.

`PageOperations` accepts one exact optional `api_id`, an optional normalized text query, an opaque next cursor, and a required page size from 1 through 50. Search covers only safe projected identifiers, protocol/name, title, organization, and purpose. Cursors bind to the plan-index digest, API filter, query, and last `(source_id, registry_operation_id)`; a changed filter or index rejects the cursor. Each page is checked against the pinned public schema before it is returned. Neither query nor response can carry endpoint URLs, paths, parameter values, credentials, quota scopes, raw errors, or provider response rows.

The time fields have separate meanings. `provider_observed_at` comes from the validated CLI observation. `health_received_at` is when Health persisted that validated result. `read_model_generated_at` identifies the current cached projection. `gatus_acknowledged_at` records the Gatus POST response; `gatus_readback_at` is a separately verified per-key Gatus observation. An acknowledgment alone never means Gatus has delivered or observed the value. Provider time must not exceed Health receive time; Gatus acknowledgment/readback must not precede Health persistence; and all event times are evaluated against the caller's current time. Future provider or persistence timestamps are shown as unobserved with `future_observation`, and future Gatus times are projected only to the last stage completed by that evaluation time. `observation_period_seconds` appears only for a bound plan, and `next_due_at` is derived from the provider observation time plus that explicit period.

Counts are unique operation identities, not attempts. `claimed` means Health durably claimed work. `attempt_state` is the latest worker claim state; `observation_attempt_state` separately says whether a validated provider observation is persisted, so a newer claim or pre-dispatch deferral does not erase the last result. Per-row `request_started` reports the validated state of the latest child receipt; `attempted` is sticky within the exact current Registry plan binding and means at least one validated CLI receipt for that plan recorded `request_started: true`. The durable store retains this bit separately from the rolling 24-attempt history, so same-plan request history survives eviction. Starting work under a changed Registry plan binding resets the public current-plan bit; prior-plan attempts stay durable but cannot be relabeled as current evidence. A missing or malformed child receipt is `unknown`, not a provider attempt. `persisted` means a validated provider observation is present. `result_state` and its allowlisted `result_category` must form a coherent pair: healthy/healthy, unhealthy/a specific failure, or indeterminate/indeterminate, observer-failure, or observation-only semantic-unknown. The `response_semantics_unestablished` category means a pinned observation-only plan received HTTP 2xx but has no documented response predicate; it is not a positive availability or credential result, and `gatus_delivery_state=not_applicable` means no Gatus push was required. A later claimed/deferred attempt may have `request_started` absent or false while this prior result remains selected; `attempted` is the sticky request evidence for the current plan. The `response_http_failure` category is limited to the observed non-2xx status on an observation-only plan and does not infer provider error class. Fresh indeterminate results remain `current_indeterminate`; they are not converted to failures. `acknowledged` and `readback_verified` remain separate; only an unacknowledged outbox row counts as `delivery_pending`. `missing` counts identities currently stale or without a validated observation. `late` counts bound identities at or past their explicit next due time without a current pass/fail/indeterminate observation. Inventory-unknown scope/operation counts are separate from missing observations and Gatus delivery counts.

The read-model cache is in-memory and immutable apart from synchronized latest-attempt updates. Its page methods do no filesystem or Gatus access. The durable attempt ledger uses schema `datapan.health-operation-attempt-store.v2` and stores one atomically replaced, bounded state file per `(source_id, registry_operation_id)`. Each snapshot carries separate bindings for the latest claim and selected observation; both are compared to the currently pinned Registry release before projection. An older observation can remain in durable history while a newer claim is shown, but it is omitted from current coverage if its plan binding differs. The current-plan sticky request bit is stored alongside a digest of the plan identity, outside the rolling attempt list. `BeginAttempt` records a fenced claim, not proof of provider traffic; only a validated child receipt can set `request_started` or persist a provider observation. A missing receipt stays ambiguous. Provider observations, Health persistence time, Gatus POST acknowledgment, and per-key Gatus readback are stored separately. Snapshot `updated_at` is the maximum timestamp among the latest claim and selected observation/delivery events represented by that projection. The snapshot reader scans and validates the bounded ledger under a shared filesystem lock for startup/background refresh, then atomically replaces the in-memory cache. This flock coordination assumes one filesystem with working `flock` semantics and does not establish a cross-host guarantee.

The production scheduler now has an opt-in plan controller that verifies the release-manifest binding, exact activation digest, generated Gatus config/map/pin, image-owned CLI bundle, durable attempt/quota/history stores, and bounded worker capacity before dispatch. An absent activation keeps the plan disabled; an invalid configured activation blocks dispatch. An active plan also gates canonical `/ready`, `/status`, and `datapan_health_scheduler_ready`, using `operation_plan_unavailable` when its capacity or current persisted evidence is unavailable. The private `/status` document explicitly partitions the original canary IDs between remaining legacy checks and exact transferred overlaps; the public reader verifies the same pinned bundle and requires current plan evidence for transferred IDs. The public reader continues to show unknown coverage until the pinned plan and persisted attempts are installed and verified. Callers must not scan per-operation files from an HTTP request. See [the runtime acceptance procedure](operation-plan-runtime.md) for required mounted inputs, local synthetic acceptance targets, and the deployment evidence boundary.
