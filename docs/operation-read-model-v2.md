# Bounded Registry operation read model

The v2 read model is a Health-owned projection over the exact Registry operation-observation-plan release and the separately pinned Korean metadata artifact. It does not replace the fixed ten-canary `/datapan/v1/status`, `/datapan/v1/dependencies`, or `/datapan/v1/services` contracts.

`schemas/datapan.health-registry-operations-page.v2.schema.json` defines a page of at most 50 operations. The page binds the Registry source revision, release-manifest digest, plan-index digest and plan-schema digest, and independently binds the API metadata revision, source snapshot digest, catalog digest, generated metadata-artifact digest, and expected entity/operation counts. Those Registry revisions are independent pins and are not required to be equal. The page carries the exact v2 schema digest separately.

Operation identity is `(source_id, registry_operation_id)`. A data.go.kr API join is accepted only when `source_id` is exactly `data_go_kr`, the operation ID matches the 64-hex `registry_operation_id` in the metadata artifact, and the plan's `dataset_id` exactly equals that metadata operation's `dataset_id` and parent `registry_api_id`. The complete operation identity sets must agree before the reader is published. ECOS, KOSIS, Open Assembly, and Seoul rows stay operation-only with `api_id: null` until their own API metadata inventories are pinned.

`NewOperationReadModel` verifies and reads each pinned plan shard once, builds sorted in-memory indexes by operation identity and API ID, and accepts a bounded list of safe metadata projections and latest durable-attempt projections. `LookupAPIProgress` accepts no more than 50 unique exact API IDs and returns per-API total functions, configured/admitted functions, current pass/fail, claimed, attempted, stale, unobserved, delivery-pending, readback-verified, and enum-keyed missing reasons. A zero-operation API is reported as `no_registered_operations`, not as a healthy API. A read-model source failure is returned as an error so the caller can mark the requested APIs unknown and show a separate source warning.

`PageOperations` accepts one exact optional `api_id`, an optional normalized text query, an opaque next cursor, and a required page size from 1 through 50. Search covers only safe projected identifiers, protocol/name, title, organization, and purpose. Cursors bind to the plan-index digest, API filter, query, and last `(source_id, registry_operation_id)`; a changed filter or index rejects the cursor. Each page is checked against the pinned public schema before it is returned. Neither query nor response can carry endpoint URLs, paths, parameter values, credentials, quota scopes, raw errors, or provider response rows.

The time fields have separate meanings. `provider_observed_at` comes from the validated CLI observation. `health_received_at` is when Health persisted that validated result. `read_model_generated_at` identifies the current cached projection. `gatus_acknowledged_at` records the Gatus POST response; `gatus_readback_at` is a separately verified per-key Gatus observation. An acknowledgment alone never means Gatus has delivered or observed the value. Provider time must not exceed Health receive time; Gatus acknowledgment/readback must not precede Health persistence; and all event times are evaluated against the caller's current time. Future provider or persistence timestamps are shown as unobserved with `future_observation`, and future Gatus times are projected only to the last stage completed by that evaluation time. `observation_period_seconds` appears only for a bound plan, and `next_due_at` is derived from the provider observation time plus that explicit period.

Counts are unique operation identities, not attempts. `claimed` means Health durably claimed work. `attempt_state` is the latest worker claim state; `observation_attempt_state` separately says whether a validated provider observation is persisted, so a newer claim does not erase the last result. Per-row `request_started` reports the validated state of the latest child receipt; `attempted` is sticky across the operation identity and means at least one validated CLI receipt recorded `request_started: true`. A missing or malformed child receipt is `unknown`, not a provider attempt. `persisted` means a validated provider observation is present. `result_state` and its allowlisted `result_category` must form a coherent pair: healthy/healthy, unhealthy/a specific failure, or indeterminate/indeterminate-or-observer-failure. Fresh indeterminate results remain `current_indeterminate`; they are not converted to failures. `acknowledged` and `readback_verified` remain separate; only an unacknowledged outbox row counts as `delivery_pending`. `missing` counts identities currently stale or without a validated observation. `late` counts bound identities at or past their explicit next due time without a current pass/fail/indeterminate observation. Inventory-unknown scope/operation counts are separate from missing observations and Gatus delivery counts.

The read-model cache is in-memory and immutable apart from synchronized latest-attempt updates. Its page methods do no filesystem or Gatus access. The durable attempt ledger stores one atomically replaced, bounded state file per `(source_id, registry_operation_id)`. `BeginAttempt` records a fenced claim, not proof of provider traffic; only a validated child receipt can set `request_started` or persist a provider observation. A missing receipt stays ambiguous. Provider observations, Health persistence time, Gatus POST acknowledgment, and per-key Gatus readback are stored separately. The snapshot reader scans and validates the bounded ledger under a shared filesystem lock for startup/background refresh, then atomically replaces the in-memory cache. This flock coordination assumes one filesystem with working `flock` semantics and does not establish a cross-host guarantee.

The source code now includes the typed reader and durable snapshot/cache-refresh interfaces with synthetic transition tests. It still does not ship the current release-manifest-bound Registry plan index/shards or a complete scheduled worker/CLI/Gatus runtime adapter. Until those release-bound inputs and adapter are present, the public source must remain unavailable and show unknown coverage rather than live results. Callers must not scan per-operation files from an HTTP request.
